quant-engine — Architecture, Explained for Absolute Beginners

The same content as the technical architecture document, rewritten for someone who has never built software or traded anything. Every section here mirrors a section there.

"Architecture", in software, just means: what are the major parts, what does each one do, and how do they talk to each other? Like a building's floor plan, but for a program.

1The 60-second summary

quant-engine is really three cooperating pieces:

  1. A worker program (qe-cli) that does the heavy lifting: invent trading strategies, test them against history, manage market data. It's written in Rust — a programming language famous for speed and for catching whole categories of bugs before the program can even run. A good choice when mistakes cost money.
  2. A server program (qe-server) — a receptionist that sits between you and the worker. It checks who you are, takes your requests ("run a backtest of strategy X over 2023"), starts the worker, watches it, and files the results.
  3. A website — the dashboard in your browser where you click buttons and see charts. Built with React, the same technology behind most modern web apps.

Everything runs on one machine, stores its data in ordinary local files, and — crucially — none of it can touch real money. The live-trading machinery exists in the codebase but is walled off so the server physically cannot reach it (§14).

A newer subsystem — a "formula-inventing robot" that evolves brand-new market indicators — plugs into the same worker/server/website trio, wrapped in an approval workflow with an audit trail (§7, §14).

2Who and what it talks to

Four parties in the system's world:

  • The admin (you) — opens the website, signs in with Google, clicks buttons to launch and review runs.
  • A developer/operator — can skip the website and drive the worker program directly from a terminal.
  • Google — used purely as the doorman: "prove this person really owns this email address." Google never sees trading data.
  • Binance (a large crypto exchange) — the eventual source of market data and, one day, the venue for orders. Today all Binance connectivity is switched off by default; the system ships with a bundled sample of historical data so everything works completely offline.
Notice what's absent: no cloud databases, no third-party analytics, no payment systems. The dependency list is deliberately tiny — fewer moving parts, fewer surprises.

3The big picture

The design has one organizing idea: the thinking is separate from the serving.

The worker (thinking)

All the number-crunching happens in the worker program, launched fresh for each job. Each job is deterministic: same inputs, same settings → identical output, byte for byte, every time. Like a calculator, not like a weather forecast. This makes results trustworthy and auditable.

The server (serving)

The server never does the math itself. It only: checks identities, accepts requests, launches worker processes, watches their progress, and serves files to your browser. Keeping it dumb keeps it safe — the part exposed to the network is the part with the least power.

They communicate the simplest way possible: the server starts the worker as a separate process and reads its progress line by line, like a supervisor reading status notes an employee slides under the door. No message queues, no microservices — boring on purpose.

4How the code is organized

The Rust code is split into 26 boxes (Rust calls them "crates"), each with one job and an explicit list of which other boxes it may use. Think departments in a company with a strict org chart. The main departments:

DepartmentPlain-language job
Vocabulary (domain) Defines the basic nouns everyone shares: what's a price bar, an instrument, a timestamp, an amount of money. Everyone speaks this language so nothing gets lost in translation.
Settings (config) Reads the configuration file and lets any setting be overridden without touching code.
Reproducibility (determinism) Controls all randomness with a seed, so "random" is repeatable and every result can be traced to exactly what produced it.
The library (storage) Stores market data in a fast embedded database (LMDB) — a filing cabinet inside the program; no separate database server to install or maintain.
Measurements & strategy DNA (signal) The indicators (standardized market measurements) and the definition of what a strategy is. The one box both the research side and the live side share — guaranteeing a strategy behaves identically in testing and in production.
Research (wfo, ensemble, ingest) Downloads history, evolves thousands of candidate strategies, and assembles the best into a diversified team. Includes the new formula-inventing robot.
Quality control (validation, gate) The statistical luck-detectors and the formal pass/fail exams a strategy team must survive.
The sealed product (vintage, formula-pool) The tamper-evident packages research produces: the strategy team ("vintage") and the evolved-formula pool. Each is stamped with a cryptographic fingerprint; change one byte and the seal visibly breaks.
Live trading (runtime, venue) The machinery for real-time evaluation, risk checks, and order handling. Built and tested — but the orders end at a simulator, and the server is forbidden from loading this department at all.
The border guard (architecture) A special box containing automated tests that verify the org chart itself — if someone wires a forbidden connection between departments, the build fails. The rules are enforced by robots, not by politeness.
Front doors (cli, server) The worker program and the server program — the only two places where departments get wired together into something runnable.

Plus web/ — the website's own codebase — and docs/, where design decisions are written down.

5The website (frontend)

What you see in the browser. Deliberately simple construction:

  • Screens: Login → then a sidebar with Backtests (list, launch, results with charts and a trade-by-trade table), Training (launch and watch a strategy search live — generation counter, progress grid, final verdict), Evolve (the formula robot: launch campaigns, inspect the evolved formulas, and walk pools through the approval workflow), and Market data (what history is on the shelves). Screens for live trading exist as greyed-out placeholders.
  • How it updates: while a job runs, the page simply re-asks the server "how's run #42 doing?" every 2 seconds — like texting "you there yet?" on repeat. Unfashionable, dead reliable, and plenty at this scale.
  • What it deliberately avoids: the fancy machinery most web apps accumulate (routing libraries, state-management frameworks). Fewer parts, fewer bugs.
  • Honesty as a feature: when the server refuses to bless a formula pool for production (which today it always does — the path is intentionally locked), the website shows the refusal and the named reasons. It never pretends success.

6The server (backend)

The receptionist in detail. It answers a short, fixed menu of requests ("API endpoints" — think numbered service-desk windows):

WindowWhat you can askWho may ask
Health"Are you alive?" (used by monitoring)Anyone
Sign-in"Log me in via Google" / "who am I?"Anyone / signed-in
RunsStart a backtest/training/evolve job; list runs; check progress; fetch results Signed-in, allowlisted users

GovernanceApprove/reject/revoke/seal a formula pool; halt a runaway job; read the audit trailSigned-in and holding the right role (§7)

Anything not on the menu gets a polite "no such window." The website itself is served by the same program, so the whole product is one process on one machine.

7Logging in & permissions

Getting in is a three-lock door:

  1. Google vouches for you. You sign in with Google; Google confirms to the server "yes, this person controls this email address." The server never sees your password.
  2. The guest list. Even with a verified email, you're only admitted if that exact address is on a pre-configured allowlist. Not on the list → turned away. If the list is missing entirely, nobody gets in ("fail-closed" — when in doubt, the door stays locked).
  3. A signed wristband. Once in, you get a browser cookie cryptographically signed by the server, valid 12 hours. Every later request shows the wristband; forging one without the server's secret key is not feasible.

Roles: not everyone can do everything

On top of "who can enter" sits "who can do what." Sensitive actions on the formula robot require a role — Operator, Approver, or Admin — assigned in server settings, never claimable by the user. The most sensitive action (blessing a formula pool for production) requires two different approvers, neither of whom launched the run — the two-keys-to-launch rule. And every governance action is written to a tamper-evident audit log: each entry is cryptographically chained to the previous one, so deleting or editing history breaks the chain visibly.

8What happens when you click "Run"

Follow one backtest from click to chart:

  1. You fill the form ("strategy package X, 2021–2024") and click Run.
  2. The browser sends the request; the server checks your wristband, sanity-checks the inputs, creates a folder for this run, and instantly replies with a receipt number.
  3. A bounded worker pool picks the job up (only a couple run at once; the rest queue politely) and launches the worker program as a separate process.
  4. The worker writes one-line progress notes as it goes; the server reads them and keeps the run's status file up to date. When finished, the worker writes the full report to disk.
  5. Your browser, asking "done yet?" every 2 seconds, sees "succeeded", fetches the report once, and draws the charts, metrics, and trade list.

An evolve (formula robot) run flows the same way, with two differences: its product is a sealed formula pool — which then enters the separate human approval lifecycle (Draft → Approved → Sealed, with Reject/Revoke exits) — and it carries extra babysitting: a ~24-hour hard time limit, and only one evolve campaign runs at a time so it can't hog the machine.

9Where data lives

No big database server anywhere. Three kinds of local storage, each fitting its job:

StoreWhat's in itAnalogy
Market library (LMDB) Years of price bars, funding rates, and metrics, indexed for very fast lookup by instrument and time. A well-organized reference library inside the building.
Sealed packages (JSON files) Strategy vintages and formula pools — each stamped with a fingerprint computed from its exact contents. The system re-checks the fingerprint on every load and refuses anything that doesn't match. Evidence bags with tamper-evident seals.
Run records (plain folders) One folder per run: parameters, live status, progress, final report. A filing cabinet — one manila folder per job.

10Settings & secrets

All behaviour is tuned via a settings file plus environment variables — named values handed to a program at startup, the standard way to configure software without editing it. The important ones, in spirit:

  • The random seed — the number that makes "random" repeatable.
  • Folder locations — where the library, packages, and run records live.
  • Network address — where the server listens. Default: this machine only, invisible to the outside world unless you deliberately change it.
  • Login settings — the Google sign-in credentials, the email guest list, and the role lists (Operators / Approvers / Admins).
  • Secret keys — for signing session wristbands and the audit log. Never written into the code or the repository; if the audit-log key is missing, audit features refuse to run rather than run unsigned.
  • Safety dials — how many jobs may run at once, the per-job time limit.

11How it's deployed

"Deployment" = getting the software running somewhere other than the developer's laptop. The repository ships a Docker recipe — a standard way to package a program with everything it needs so it runs identically anywhere, like a sealed meal-kit instead of a loose recipe. The recipe builds the worker program in one step and produces a slim final image, with all data kept on an attachable storage volume so upgrading the software never touches the data.

There is currently no automation for pushing releases to a cloud provider — a deliberate "not yet": the system is still in its research phase, running for one operator on trusted machines.

12Quality control & monitoring

  • Automated checks: every proposed code change normally runs a gauntlet — code formatting, a strict "linter" (an automated nitpicker), the full test suite (~1,100 tests, including the tests that police the department walls of §4/§14), and a dependency-license/vulnerability audit.
  • Logs: the system writes structured, machine-readable logs stamped with which run, which strategy package, and which instrument each message concerns — so an investigator can pull one thread cleanly.
  • Health check: a simple "are you alive?" endpoint for monitoring tools.
Honest caveat: those automated checks were temporarily switched off during an intense July 2026 development push, and turning them (and the "no unreviewed changes to the main branch" rule) back on is a recorded outstanding chore. The checks themselves are unchanged and ready.

13Long-running jobs

Training or evolve runs can take hours. The taming mechanisms, in plain terms:

  • A bounded crew: only a fixed number of jobs run simultaneously (default 2); extras wait in a queue.
  • No zombie processes: jobs are started with a dead-man's switch — if the server stops or a run is aborted, its worker process is killed rather than left running forever.
  • A curfew: each run has a hard wall-clock limit (~24h); overrun → killed and marked failed.
  • An emergency stop: an authorized Operator can halt any run from the dashboard.
  • Terminal honesty: a failed run stays failed — no silent auto-retries that could paper over a real problem.

14Security walls

Layered walls, outermost first:

  1. The network wall. The server listens only on the local machine by default and every meaningful request requires the signed session wristband (§7).
  2. The guest list + roles. Allowlisted emails only; destructive/governance actions additionally require assigned roles; production-blessing requires two independent approvers.
  3. The big one — the internal firewall. Automated tests forbid entire departments from knowing each other: the strategy-inventing code can never reach the live-trading code, and the network-facing server can never load the live-trading department at all. Even a bug — or a malicious change — in the server cannot place an order, because the order-placing machinery isn't in the building. The wall is checked by robots on every change.
  4. Sealed artefacts. Strategy packages and formula pools are fingerprinted; anything that fails verification is refused, so results can't be quietly doctored after the fact.
  5. The audit chain. Governance actions land in the tamper-evident, cryptographically chained log (§7).
  6. Fail-closed defaults everywhere. Missing guest list → nobody enters. Missing audit key → auditing refuses to run. Formula-pool production path → locked until its required evidence exists. When configuration is incomplete, the system chooses "safe and unhelpful" over "helpful and unsafe".
  7. No real orders, full stop. The strongest guarantee is structural: the live order-submission code has not been written. You cannot accidentally trade real money with software that contains no way to do so.

15Known weak spots (the honest list)

Straight from the technical doc's risk register, translated. That these are written down and ranked is itself a good sign — mature projects keep honest lists.

Weak spotPlain meaningSeverity
No traffic encryption built in The server itself speaks plain HTTP. Fine while it listens only on the local machine; before facing the internet it must sit behind a standard encrypting proxy. High
Automated checks temporarily off The §12 caveat: CI and branch protection need switching back on. High
Sessions may not survive a restart If the wristband-signing key isn't configured, the server invents a temporary one — safe, but every restart logs everyone out. Should refuse to start in production without a real key. High
Data downloading is a placeholder The real "fetch fresh data from the exchange" plumbing is stubbed; the system currently leans on its bundled sample data. Medium
Formula robot's production path incomplete The final lock on the evolve→production path stays closed until one category of required evidence is produced. Deliberate ordering: lock first, key later. Medium
No automated release process Deploying a new version is manual. Fine for one operator; would need automation before a team relies on it. Medium
Progress via polling; stored data unencrypted; a database sharp-edge Assorted small items: the 2-second "done yet?" polling would need upgrading only with many simultaneous users; files on disk rely on disk-level encryption; and the embedded database has a known "open it only once" rule the code carefully respects.
