# QE-483 — Serialise the governance-cache read-modify-write in `apply_cache_transition` under a per-pool async lock (or document it as audit-derived and rebuildable)  *(R5 — panel review 2026-07-31, P2)*

> **Status:** Todo — [panel review](../../reviews/panel-review-2026-07-31.md) · [backlog index](../../backlog.md) · [spec](../../specs.md)

`Phase: Review R5 (panel review)` · `Area: server (governance cache)` · `Depends on / relates to: QE-454 (audit chain = source of truth); relates to QE-473 (chain verification at seal)`

**Why.** `apply_cache_transition` (`crates/server/src/pools.rs:862`) reads the governance record, applies the transition, and writes it back — `pools.governance(id)` read (pools.rs:869), `governance.apply(...)` (pools.rs:878), `pools.governance.write(&governance)` (pools.rs:881-884) — with **no lock spanning the read-modify-write**. Two concurrent approve/seal requests for the same pool can interleave read → write and lose one update (last-write-wins). The engine already knows how to guard analogous RMWs: the run store holds `self.index_lock.lock().await` across the discovery-index read-modify-write await (`crates/server/src/runs/manager.rs:217`), and the authoritative audit append is serialised under `append_lock` (`crates/server/src/audit.rs:359`). The governance cache is the one RMW left unguarded. The blast radius is **narrow by construction**: per the crate docstring (`audit.rs:11-14`), `governance/<pool>.json` is a *rebuildable cache the seal gate never reads* — the tamper-evident audit chain is the authoritative source of pool approvals, and `derive_signoff` (audit.rs:435-455) re-derives sign-off from the chain, not from this record. So a lost cache write cannot forge or drop a real approval; it can only make the **displayed** lifecycle state briefly diverge from the chain. Still worth fixing for display honesty and to remove the surprising unguarded RMW.

**Scope / requirements.**
- **Preferred: serialise the RMW.** Guard the `governance(id)` → `apply` → `governance.write` sequence (pools.rs:869-884) with a per-store (or per-pool) async `Mutex` held **across** read → apply → write, mirroring `index_lock` (`manager.rs:217`). A per-pool keyed lock (map of `pool_id → Mutex`) avoids serialising unrelated pools; a single coarse cache lock is acceptable given the low governance volume. If `apply_cache_transition` runs inside `spawn_blocking`, take the async lock in the caller and pass the guard through, or make the cache write path async.
- **Alternative (equally acceptable): document + derive.** If a lock is judged unnecessary, add an explicit doc comment on `apply_cache_transition` stating the record is an **eventually-consistent, audit-derived cache** that is authoritative nowhere, and ensure any read that matters re-derives lifecycle from the audit chain (`derive_signoff` / chain replay) rather than trusting the cached record. Choose one path, not both half-done.

**Out of scope.** The authoritative audit chain and its ordering (`append_lock`, audit.rs:359) — unchanged; this ticket does not touch the source of truth. The seal predicate `seal_allowed` / `derive_signoff`, which already ignore this cache. The `index_lock` run-store path (QE-411). Chain verification at seal time (QE-473 owns that).

**Acceptance criteria.**
- **Path A:** a test with two racing approve/seal transitions on the **same** pool serialises the cache RMW — no lost update; the final cached state equals the sequential result — while transitions on **different** pools are not needlessly serialised (if a per-pool lock is used).
- **Path B:** an explicit doc comment **and** an inline code comment on `apply_cache_transition` state the cache is derived-and-rebuildable from the audit chain, and a test/assertion confirms the load-bearing lifecycle read re-derives from the chain rather than the cached record.
- Authoritative audit append ordering (`append_lock`) is unchanged and its serialisation test (if any) stays green.
- Server-only change: no QE-006 core, vintage content hash, or `VINTAGE_FORMAT_VERSION` impact.
