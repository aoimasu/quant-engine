# QE-489 — Resolve firewall edges by the dependency's TARGET (`package =` / `path =`), not the manifest key, so an internal crate under a non-`qe-` key cannot bypass the firewall  *(R5 — panel review 2026-07-31, P2)*

> **Status:** Todo — [panel review](../../reviews/panel-review-2026-07-31.md) · [backlog index](../../backlog.md) · [spec](../../specs.md)

`Phase: Review R5 (panel review)` · `Area: architecture (firewall)` · `Depends on / relates to: none`

**Why.** `parse_manifest` (`crates/architecture/src/lib.rs:38`) records a dependency edge **only when the manifest KEY starts with `qe-`**: the dependency-table form inserts only when `dep.starts_with("qe-")` (`lib.rs:50-53`), and the inline form matches `SectionKind::ProdDeps if line.starts_with("qe-")` (`lib.rs:61`). The graph is therefore built from the dependency **key**, not from the resolved `package = "..."` / `path = "..."` **target**. An internal workspace crate pulled in under a non-`qe-` key — a `package =` rename (`foo = { package = "qe-live", ... }`) or a bare `path = "../search"` dep whose key is not `qe-`-prefixed — is **invisible** to the firewall, so a forbidden edge (e.g. `live → search`) would sail through CI **green**. **Verification (latent, deliberate-bypass-only):** there are zero live evasions today — the sole `path =` dep in the tree (`qe-domain`) keeps a `qe-` key and *is* caught, and the idiomatic `qe-foo.workspace = true` form is always caught. The hole is a latent bypass, not an active leak, but it defeats the firewall's fail-closed intent: an architectural boundary that can be silently crossed by renaming a key is not a boundary.

**Scope / requirements.**
- Resolve each dependency edge by its **target**, not its key. Parse the `package = "..."` value (dependency-table form and inline form) and use the real package name as the edge target; where a dep specifies `path = "../<crate>"` pointing under `crates/`, treat it as an **internal** dependency regardless of the key's prefix, mapping the path to the target crate's real package name before building the graph.
- Handle the inline table form too (`foo = { package = "qe-live" }` / `foo = { path = "../live" }`) in the `ProdDeps` branch (`lib.rs:61-67`), not only the bare `qe-foo.workspace = true` shape — extract `package`/`path` from the inline table rather than taking the key prefix.
- **At minimum** (if full path→package resolution is deferred): assert that every dependency key which resolves to a workspace member is `qe-`-named — i.e. fail the firewall build if any manifest pulls a workspace crate under a non-`qe-` key. This closes the bypass fail-closed even before full target resolution lands.
- Keep the existing structural section classification (`classify_section`, `SectionKind`, dev-dependency exclusion) unchanged; only the *edge-target extraction* changes.

**Out of scope.** The forbidden-edge policy itself (which crate may depend on which) and the dependency-cycle checks — this ticket fixes edge *discovery*, not the rules applied to edges. Dev-dependency handling (still excluded from the production firewall in every form). External (crates.io) dependencies — only workspace-member targets matter to the firewall.

**Acceptance criteria.**
- A unit test that an internal crate pulled under a **non-`qe-` key** is still detected: both a `package = "qe-runtime"` rename under a non-`qe-` key AND a bare `path = "../search"` dep produce a firewall edge to the real target crate (or, under the minimum variant, fail the `qe-`-named-key assertion).
- A regression test that the existing idiomatic detection stays green: `qe-foo.workspace = true`, the `[dependencies.qe-foo]` table form, `target.*` platform forms, and the live `qe-domain` `path =` dep are all still caught exactly as today.
- Dev-dependencies remain excluded in every form (existing exclusion test stays green).
- Determinism: `parse_manifest` output (`BTreeSet<String>` of deps) is order-stable for a given manifest; no wall-clock, no filesystem-order dependence in edge enumeration.
