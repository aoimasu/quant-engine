# QE-496 — Fold the effective run parameters into the vintage/pool lineage id so distinct runs cannot silently overwrite each other's sealed artefacts  *(R6 — fleet run 2026-08-01, P0)*

> **Status:** Done (this PR) — [fleet findings report](../../reviews/) · [backlog index](../../backlog.md)

`Phase: Review R6 (real-data fleet run)` · `Area: cli (lineage construction) / determinism` · `Depends on / relates to: QE-006 (lineage), QE-129 (config content hash), QE-448 (universe provenance)`

**Why.** The vintage id is the [`Lineage::id`] — a hash over `{config_hash, input_snapshot_id, code_commit, seeds}`. `run_train` built it as `Lineage::from_config(cfg, "", code_commit, vec![seed])` (`crates/cli/src/lib.rs:129` pre-fix): the `input_snapshot_id` slot was hardcoded **empty**, and every effective CLI knob — `--start/--end/--resolution/--generations/--population/--holdout/--embargo/--windows/--folds/--indicator` — bypasses the config, so none of them entered the hash. Consequence, **independently reproduced by three fleet lanes on real data**: two trains with the same seed but different windows (lane q2), different search budgets (q3), or different WFO geometry (q4) produce the **same vintage id**, and the repository write **silently overwrites** the earlier sealed artefact — the fleet's own leaderboard contained an overwrite victim (`d5de8d97…` sealed under two different train windows). This contradicts the README's content-addressing claim ("same config + seed + commit reproduces the same vintage" is true, but *different* runs must never share an id) and destroys artefact lineage for any parameter sweep. `run_evolve` (`lib.rs:224` pre-fix) had the identical hole for pool campaigns.

**Scope / requirements.**
- **Fingerprint the effective parameters into the lineage.** New `run_fingerprint(kind, parts)` (`crates/cli/src/lib.rs`): SHA-256 over `kind` + ordered `key=value` lines, emitted as `params-sha256:<hex>` into the previously-empty `input_snapshot_id` slot — **no `Lineage` schema change**, no vintage-format change, and the self-describing prefix cannot be mistaken for a future real ingest-snapshot id.
- **Train:** fingerprint `{instrument, start, end, resolution, generations, population, holdout, embargo, indicator_subset, windows, folds, flow}`. **Evolve:** fingerprint `{instrument, start, end, resolution, mode, generations, offspring, states, k}`.
- **Determinism preserved (QE-006):** identical inputs ⇒ byte-identical fingerprint ⇒ identical vintage id; the reproducibility contract is unchanged — only *distinct* runs now separate.
- **Sealed history unaffected:** already-sealed artefacts carry their own stored lineage (fixtures use `"fixture-snapshot"`); ids of existing artefacts do not move. Only newly-sealed runs get the richer id.

**Out of scope.** A real input-data snapshot id (the ingest-snapshot stages own that; when they land, the snapshot id and the params fingerprint should compose — e.g. `snapshot:<id>+params-sha256:<hex>`). Retro-rehashing existing artefacts. The `Lineage` struct/serde shape.

**Acceptance criteria.**
- Unit test (`run_fingerprint_separates_every_effective_parameter`): identical inputs byte-stable; a changed window, changed budget, and train-vs-evolve kind each produce a distinct fingerprint; `key=value` concatenation is boundary-unambiguous. **[met]**
- Two `run_train` invocations differing only in a CLI knob produce distinct lineage ids (empirically reproduced by the fleet pre-fix; the unit test pins the mechanism post-fix). **[met]**
- Same-input reproducibility: the existing determinism tests (same seed ⇒ same vintage id) stay green. **[met — full suite]**
- No `VINTAGE_FORMAT_VERSION` bump (no schema change); fixtures untouched.

`Spec ref: fleet run 2026-08-01, findings q2/q3/q4 (high severity, independently reproduced). Touches crates/cli/src/lib.rs (run_train, run_evolve, run_fingerprint) + Cargo.lock (sha2 → qe-cli, already in-tree).`
