# QE-473 — Verify the audit hash-chain (`verify_chain`) inside `production_seal` before dual sign-off, refusing to seal on a broken chain  *(R5 — panel review 2026-07-31, P0)*

> **Status:** Todo — [panel review](../../reviews/panel-review-2026-07-31.md) · [backlog index](../../backlog.md) · [spec](../../specs.md)

`Phase: Review R5 (panel review)` · `Area: server (governance / audit / seal)` · `Depends on / relates to: QE-454 (audit chain + seal governance)`

**Why.** The single irreversible production-seal decision is made from an **unauthenticated JSONL read**. `production_seal` reads the log with `audit.read_all()` (`crates/server/src/pools.rs:478`) and the seal predicate `seal_allowed` (`crates/server/src/pool_seal.rs:61`) dispatches dual sign-off to `AuditLog::derive_signoff` (`crates/server/src/audit.rs:435-455`), which counts distinct `approve` entries reading **only** `e.action` / `e.subject_hash` / `e.actor_email` (audit.rs:443-447) — it never touches `entry_hash`, `hmac`, or `prev_hash`. The tamper-evidence machinery `AuditLog::verify_chain` (`audit.rs:398`) is invoked in exactly **one** place: the read-only display handler `get_audit` (`audit.rs:67`) — a grep of the server crate confirms **zero** calls in `pools.rs` / `pool_seal.rs`. So an actor able to append two forged `approve` lines (garbage `hmac`/`entry_hash` fields, two distinct emails, both bound to the target `pool_hash`) satisfies `TwoDistinctSignoffs` (audit.rs:453) and seals production. `verify_chain` **would** catch the bad HMAC/linkage (`ChainStatus::BrokenAt`, audit.rs:403-423) but is not run at seal time. The crate docstring (`audit.rs:19-20`) frames chain+HMAC as "tamper-*evidence*, sufficient for v1" — which makes it **load-bearing at the one moment that matters**, and it is currently unused there. Violates the fail-closed invariant: the seal gate trusts unverified append-only bytes.

**Scope / requirements.**
- At the top of `production_seal` (`crates/server/src/pools.rs:469`), immediately after `audit.read_all()` (pools.rs:478) yields `entries`, call `audit.verify_chain(&entries)`.
- On `ChainStatus::BrokenAt { seq }`, **refuse to proceed**: return `409 Conflict` with a named blocker (`"audit chain integrity check failed at seq {seq} — refusing to seal"`) and take the same rejected-attempt branch the predicate uses for other blockers. Do **not** call `resolve_launcher` / `seal_allowed` / mark-sealed on a broken chain.
- Route the `verify_chain` call so it does not block the async worker (it is pure CPU over an already-read `Vec`; fold it into the existing `spawn_blocking` that runs `seal_allowed`, or verify inside the same blocking closure that reads revocations). The chain is already fully in memory, so the added cost is a single linear pass — trivial.
- Keep `verify_chain` the sole authority on chain validity — do not reimplement HMAC/linkage checks in `pools.rs`; call the existing method.

**Out of scope.** The `derive_signoff` sign-off arithmetic (audit.rs:435-455) — it stays hash-blind by design; QE-473 gates it behind a verified chain rather than changing it. The `get_audit` display path (audit.rs:64). External WORM checkpointing of the chain head (the docstring's named follow-up, audit.rs:20). Any change to `SealDecision` blocker semantics beyond adding the new chain-integrity blocker.

**Acceptance criteria.**
- A unit/integration test: a pool whose audit log carries two forged `approve` entries with **invalid HMACs** (or a broken `prev_hash` linkage) does **not** seal — `production_seal` returns `409` / the chain-integrity blocker, and `mark-sealed` is never reached.
- A companion test: a pool with a **valid** chain and two genuine distinct sign-offs still seals successfully (no regression to the happy path).
- The `verify_chain` call runs off the runtime worker (no synchronous verification on an async body) and over the already-read entries (no second `read_all`).
- Determinism / QE-006 core untouched: this is server governance only; no vintage content hash or `VINTAGE_FORMAT_VERSION` change.
