# QE-470 — SPIKE: does an activity clock (dollar / volume bars) earn its integration cost? *(R3 — AFML panel #3, investigation)*

> **Status:** Spike / Todo — [gap analysis](../../afml-gap-analysis.md#contest-2--are-dollar-bars-worth-the-pipeline-rebuild) · [backlog index](../../backlog.md) · [spec](../../specs.md)
>
> **This is a spike, not an implementation ticket.** Deliverable = a written recommendation + evidence, to be discussed. **Do not** rebuild the bar pipeline under this ticket. Timebox: ~2–3 days.

`Phase: Review R3 (AFML panel)` · `Area: (investigation) domain / ingest / storage / wfo` · `Sequenced AFTER: QE-468, QE-469`

**Why (the open question).** *Advances in Financial Machine Learning* Ch. 2 (pp. 26–34) is emphatic:
avoid time bars — they over/under-sample activity and yield heteroscedastic, serially-correlated,
non-Normal returns — and prefer an activity-subordinated clock (tick → volume → **dollar** bars), with
information-driven **imbalance/runs** bars best of all. The engine today samples on a **wall-clock**
grid only: `crates/domain/src/resolution.rs` enumerates M1…D1 and nothing else; `crates/domain/src/bar.rs`
is a time-keyed OHLCVT candle; the backtester walks a `Vec<Bar>` on that fixed grid.

The panel **agreed on the direction** but **split on the payoff**, and the disagreement is real enough
to warrant evidence before committing:

- **For (trader, SWE):** crypto's ~100× price range over the sample makes the dollar-bar argument
  *stronger* than the book's equities example; and the engine's own `(qty/ADV)^β` slippage term proves
  activity varies wildly, so **time bars are silently mis-weighting the very impact term the backtest
  depends on**.
- **Against / caution (quant, integration):** crypto trades ~24/7, so it lacks the session open/close
  activity clustering that motivates dollar bars for the E-mini — the near-IID-Normal payoff may be
  smaller here. And the integration cost is real and touches load-bearing invariants (below).

Because the payoff is genuinely uncertain and the change is the most invasive of the three AFML
adopt-items, we **measure first**. Critically, this spike is sequenced **after QE-468/469** so the
comparison is judged against a *trustworthy, deflated* Sharpe rather than the currently-inflated one.

**Questions the spike must answer (with evidence).**
1. **Distributional payoff.** On a representative sample (≥ 2 liquid perps + ≥ 1 thin-alt), build
   offline dollar bars and volume bars from `aggTrades` and measure, vs the current time bars: return
   normality (e.g. Jarque–Bera / kurtosis), return autocorrelation, and bar-count-per-day stability.
   Does the book's claimed near-IID-Normal improvement actually materialise for USDT-M perps, and by
   how much? Quantify — don't assert.
2. **Does it move the deflated metric?** Re-run a small fixed set of *already-sealed* strategies (or a
   short GP search) on the activity clock and compare **QE-468 daily/Lo-adjusted Sharpe + QE-469 CPCV
   DSR distribution** vs the time-bar baseline. Is there a statistically meaningful improvement in the
   *deflated* verdict, or only in the raw (already-suspect) number?
3. **Data dependency.** Confirm the `aggTrades` ingest gap: today ingest is klines-only
   (`crates/ingest/src/binance.rs` — "klines-only slice … does not fetch aggTrade";
   `crates/ingest/src/source.rs` `DataKind` has no trades variant). Scope what a `DataKind::AggTrades`
   path costs (volume, storage, backfill) — this is a **prerequisite**, so its cost is part of the
   payoff calculation.
4. **Integration-cost inventory.** Document, concretely, what an activity clock breaks and the
   proposed fix for each:
   - **Funding alignment** — funding is an 8h wall-clock cashflow (`crates/wfo/src/backtest.rs`
     funding accrual). Proposed answer to validate: **accrue funding on the real wall-clock stamp
     regardless of bar clock** so the perp cashflow stays correct.
   - **Storage key scheme** — `crates/storage/src/key.rs` encodes a resolution byte in an
     order-preserving key. Proposed answer: **widen the tag to `{time|dollar|volume}` + size** so
     activity bars coexist with klines without collision or range-scan breakage.
   - **Purged-CV horizon arithmetic** — `purge = max_lookback + label_horizon` is expressed in **bar
     counts** (`crates/wfo/src/cv.rs`). Proposed answer: **re-express horizons in the new bar units**
     and confirm the leakage invariants still hold.
   - **Determinism** — bar construction from ticks must be byte-deterministic under the QE-006 harness
     (tie-breaking on exact tick boundaries).

**Deliverable.**
- A short written recommendation — **adopt / defer / drop** — in `docs/operations/` (analysis doc) or
  `docs/architecture/` (if it becomes a design), with the measurements from Q1–Q2, the data-cost
  scope from Q3, and the integration-cost inventory from Q4.
- If **adopt**: a follow-up implementation ticket (or ticket set) is filed with the integration plan
  from Q4; **this spike does not implement it.**
- If **defer/drop**: record *why* (which measurement fell short) so it is not re-litigated from
  scratch — this ticket is the durable home for that decision.

**Out of scope.** Any production change to `Resolution`/`Bar`, the storage key, ingest, or the
backtest loop. Imbalance/runs bars (a further step beyond dollar/volume — note them as a possible
phase 2 in the recommendation, don't build them). VPIN order-flow features (tracked separately as
AFML rec #7).
