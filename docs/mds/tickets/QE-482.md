# QE-482 — Enforce the hash-stable rounding invariant at the seal type boundary, not just producer-side  *(R5 — panel review 2026-07-31, P1)*

> **Status:** Todo — [panel review](../../reviews/panel-review-2026-07-31.md) · [backlog index](../../backlog.md) · [spec](../../specs.md)

`Phase: Review R5 (panel review)` · `Area: vintage` · `Depends on / relates to: QE-467 (persisted seal evidence); relates to QE-476 (sealed verdict)`

**Why.** `VintageContent::content_hash` (`crates/vintage/src/lib.rs:490`) is SHA-256 over
`serde_json::to_vec(self)`, and both the vintage id and its on-disk key derive from that digest. The
hashed content includes raw `f64` vectors — `weights`, `holdout_series.returns`, and the
`SealEvidence`/`CpcvSummary` figures. The crate docstrings state the reproducibility precondition
explicitly — "the seal writer rounds each return to a **hash-stable precision** (like `weights`) so it
round-trips byte-identically" (`lib.rs:119-120`, and again at `lib.rs:172-173` for
`HoldoutReturnSeries`). But `VintageContent::validate` (`lib.rs:410-477`) — the **only** gate
`Vintage::seal` (`lib.rs:512`) runs — checks **finiteness and alignment only**: weight/chromosome length
(`lib.rs:411-415`), per-value `is_finite` on weights, holdout returns, evidence figures, and CPCV
vectors. There is **no rounding and no precision check**. The rounding is enforced *producer-side only*,
in the train job's `hash_stable` (`crates/cli/src/jobs/train.rs:106-114`, `HASH_STABLE_SCALE = 1e12`). A
future seal writer that constructs a `VintageContent` without routing every f64 through `hash_stable`
still passes `seal()`/`verify()`, yet two runs of the same lineage produce **different content hashes** —
an undetectable break of the content-addressed reproducibility guarantee (QE-006). The invariant lives in
a comment and a caller, not in the type that owns the hash.

**Scope / requirements.**
- **Move the rounding invariant into the type boundary.** Have `Vintage::seal` (or `VintageContent`
  canonicalisation it calls) canonicalise **every hashed f64 field** to the fixed hash-stable precision
  before hashing — `weights`, `worst_case_loss`, `holdout_series.returns`, every `SealEvidence` scalar
  and `Option`, and the `CpcvSummary` summary fields + `path_sharpes`/`path_dsrs`. Reuse the same
  `1e12`-scale rounding rule `hash_stable` applies (lift it into `qe-vintage`, or expose a shared
  helper) so producer and type agree by construction.
- **Alternative acceptable posture: reject, don't silently round.** If canonicalising in `seal` is
  undesirable, `validate` must instead **reject** any hashed f64 that is not already at the hash-stable
  precision (a new `VintageError` variant), turning the silent divergence into a fail-closed seal error.
- Keep the finiteness/alignment checks in `validate` exactly as they are — this adds a precision
  invariant alongside them, it does not replace them.

**Out of scope.** The `hash_stable` producer helper in `train.rs` (it stays; after this it becomes
belt-and-braces, not the sole guarantor). The CPCV distribution *computation* (QE-469). The
`serde_json` canonical-ordering property. Any change to which fields are hashed.

**Acceptance criteria.**
- An idempotence test: `Vintage::seal(content).content_hash == Vintage::seal(round(content)).content_hash`
  for a `content` whose f64 fields carry sub-precision noise — i.e. seal is invariant to pre-rounding.
- A test that a `VintageContent` with a **non-hash-stable** f64 either canonicalises to the same hash as
  its rounded twin (canonicalise posture) or returns a seal error (reject posture) — pick one and prove it.
- Determinism: two seals of the same lineage on different machines produce byte-identical vintage ids
  (QE-006 harness green).
- If the on-disk schema changes at all, exactly **one** `VINTAGE_FORMAT_VERSION` bump (currently `8`,
  `lib.rs:55`) via the real seal path, goldens regenerated intentionally (QE-467 single-bump discipline).
